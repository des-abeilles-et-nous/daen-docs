# Subscriptions

Subscriptions express a user's standing interest in events that match a filter — typically "notify me when a POI of type X appears within Y km of location Z". They are the registration step in the event delivery pipeline; the firing step lives in [Feeds](Feeds.md).

For raw JSON shape sketches, see [mdd daen-scout.md](mdd%20daen-scout.md) (RTDB section, `subs` path).

---

## Storage

| Location | Path | Purpose |
|---|---|---|
| Realtime Database | `/subs/{subsId}` | Subscription document. `subsId` is auto-generated by `push()`. |
| Realtime Database | `/feeds/{feedId}/subs/{subsId}` | Reverse index — feed → listeners. Maintained by `triggerSubsAlerts`. |
| Firestore | `users/{uid}.subs[]`, `users/{uid}.alerts[code].subsid` | User-side ownership and per-alert pointer (see [User model](User%20model.md)). |

RTDB is used because subscription state is mutable, frequently appended-to (event logs), and benefits from realtime listeners.

---

## Field shape

| Field | Type | Required | Description |
|---|---|---|---|
| `uuid` | string | yes | Owner's user UID. Validated by RTDB rules. |
| `feeds` | string[] | yes | Feed IDs the subscription listens to. Typically tile IDs (e.g. `"1\|23\|45"` from `POI.tileIdFromLatLon`). |
| `status` | string | yes | Subscription state: `"active"`, `"new"`, `"notified"`, `"read"`, `"archived"`, `"frozen"`. |
| `trigger` | string | yes | Event type to match: `"poi-new"`, `"poi-update"`, `"*"` (any). |
| `mode` | string | optional | Firing policy. See [Modes](#modes) below. |
| `name` | string | optional | Human-readable label (e.g. `"HORNET in 5km from {lat,lon}"`). |
| `opts` | string \| object | optional | Trigger options. Most commonly a POI-type substring filter (e.g. `"HORNET/ASIAN"`); `"*"` means any. |
| `filter` | number \| string | optional | Geographic filter — distance in km (haversine). `"*"` or undefined = no distance filter. |
| `fopts` | object | optional | Filter parameters; see [Filters](#filters) below. |
| `fopts.latitude` | number | conditional | Reference latitude (when `filter` is a distance). |
| `fopts.longitude` | number | conditional | Reference longitude. |
| `fopts.{code}` | boolean | conditional | For `mode: "firstof"` — tracks which POI codes have already triggered. |
| `logs` | map | optional | Event log keyed by event UID. Populated by `notifySubs` from feed events. |
| `logs.{eventId}.event` | string | conditional | Event type copied from the feed event. |
| `logs.{eventId}.params` | object | conditional | Event params (`{code, poi, lat, lon}`, etc.). |
| `logs.{eventId}.at` | number | conditional | Event timestamp (ms). |

## Modes

`mode` controls how a subscription behaves once it fires.

| Mode | Behaviour | Use case |
|---|---|---|
| `"all"` (default) | Fires on every matching event. Sub stays active indefinitely. | Standing alerts ("any new hornet near me"). |
| `"once"` | Fires once, then auto-deletes. | Single-shot alerts ("notify me the next time X happens"). |
| `"firstof"` | Fires once **per distinct POI code**. Tracks fired codes in `fopts.{code} = true`. | "First of each kind" digest ("first hornet, first nest, first swarm"). |
| `"*"` | Aliased to `"all"`. Redundant — see open questions. | — |

**Source:** [`db-triggers/subs.js`](https://github.com/des-abeilles-et-nous/daen-fb-workers/blob/main/functions/db-triggers/subs.js) (lines ~75–88).

## Filters

### POI type filter (`opts`)

A substring match against the event's `params.code`:

```js
// Subscription
{ opts: "HORNET/ASIAN" }

// Matches event with params.code = "HORNET/ASIAN/NEST"
// Does not match params.code = "BEE/SWARM"
```

`"*"` or undefined disables the type filter.

### Geographic filter (`filter` + `fopts.latitude/longitude`)

Distance in kilometres from a reference point, computed via haversine over `params.lat/lon`:

```js
{
  filter: 5,
  fopts: { latitude: 48.8566, longitude: 2.3522 }
}
```

`"*"` or undefined disables the distance filter.

### Combination

Both filters apply as **AND**: the event passes only if it matches the type filter (or none is set) **and** is within the distance (or none is set). See [`subs.js`](https://github.com/des-abeilles-et-nous/daen-fb-workers/blob/main/functions/db-triggers/subs.js) (lines ~98–100, 167–200).

## Lifecycle

```
Create → Activate (register on feeds) → Match (event arrives) → Evaluate filters → Alert → Update mode state → (Modify | Delete)
```

### 1. Create

Triggered by user action in daen-scout (e.g. tapping "alert me" on a map area):

1. `createUserSubscription()` writes a new doc to `rtdb:/subs/{newId}` with `uuid`, `feeds[]`, `status: "active"`, `trigger`, `name`, `mode`, `opts`, `filter`, `fopts` ([`fb-user.js`](https://github.com/des-abeilles-et-nous/daen-fb-workers/blob/main/functions/lib/daen-firebase/fb-user.js), lines ~123–147).
2. `addSubs2user()` appends `newId` to `user.subs[]` ([`fb-user.js`](https://github.com/des-abeilles-et-nous/daen-fb-workers/blob/main/functions/lib/daen-firebase/fb-user.js), lines ~154–165).

### 2. Activate

`subs-triggerSubsAlerts` fires on the write and registers the subscription with each feed:

- For each `feedId` in `subscription.feeds[]`, set `rtdb:/feeds/{feedId}/subs/{subsId} = {trigger, opts}`.
- The feed now knows this sub is listening (used by `notifySubs` on event arrival).

### 3. Match

When a feed event lands at `rtdb:/feeds/{feedId}/logs/{logId}`:

1. `feeds-notifySubs` fires (see [Feeds](Feeds.md)).
2. It walks `feeds/{feedId}/subs/*` and copies the event into `subs/{subsId}/logs/{eventId}` for each sub whose `trigger` and `opts` match at this coarse level.

### 4. Evaluate

The append to `subs/{subsId}/logs` re-fires `subs-triggerSubsAlerts`, this time with new logs to evaluate:

1. For each new log entry, apply the geographic filter (`filter` + `fopts.lat/lon`) against `params.lat/lon`.
2. If passed, call `triggerAlertIfNeeded()` → `notifs.sendUserAlert()` (push notification via Expo).
3. Update mode state:
   - `"once"` → delete the subscription entirely.
   - `"firstof"` → set `fopts.{code} = true` to mark this code as fired.
   - `"all"` / `"*"` → no state change.

### 5. Modify

When a user edits an alert (changes filter, opts, trigger):

1. Client updates `rtdb:/subs/{subsId}` directly.
2. `subs-triggerSubsAlerts` re-fires and **re-syncs the per-feed registration** with the new `trigger`/`opts` (lines ~137–147).

### 6. Delete

Two paths, both deterministic:

- **User-driven:** client removes `subsId` from `user.subs[]`. The Firestore `onUserChange` trigger detects this and deletes `rtdb:/subs/{subsId}`. See [User model § Profile updates](User%20model.md#2-profile-updates).
- **Mode-driven:** `mode: "once"` self-deletes after firing.

When the sub document is deleted, `triggerSubsAlerts` running on the delete event also clears the per-feed reverse-index entries (`feeds/*/subs/{subsId}`).

| User | `subscription.uuid` | Owner. |

## Open questions

1. **`mode: "*"` vs `"all"`.** The code treats them identically (`subs.js` ~76–77). Either historical noise or signalling intent that has not yet diverged.
2. **`firstof` reset on edit.** When a user modifies a `firstof` subscription (e.g. changes `opts`), the `fopts.{code}` flags are not reset, so codes already fired under the old config remain "seen" under the new config. Likely a bug, but possibly intentional rate-limiting.
3. **`name` field usage.** Set on creation but never read or updated by the surveyed code. Inspect daen-scout client to confirm if it is the UI label or an admin-only diagnostic.
4. **Empty `feeds[]`.** Rules do not validate non-empty `feeds[]`. A subscription with no feeds is a no-op (never matches anything) but is otherwise valid. Worth a client-side guard.
5. **`status` transitions.** The schema declares six possible values but only `"active"` is set on creation. The transitions between `new`/`notified`/`read`/`archived`/`frozen` are not exercised in the surveyed code — is this an aspirational state machine, or is the logic elsewhere (admin? client?)?
